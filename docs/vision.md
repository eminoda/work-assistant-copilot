# 愿景与定位

## 一句话

WorkCopilot 是基于 **Browser Agent + Desktop Agent + AI Runtime** 的个人工作助手。

## 愿景

融入日常办公工作流，为各个环节提供高效方案，**释放双手，把时间留给思考与沉淀**。

它不是「再做一个 RPA 控制台」，而是：

- 在浏览器里**就近**完成触发与录制；
- 在桌面端**承接**执行、存储、定时与通知；
- 用本地 AI Runtime **编排**工具与记忆，而不是让模型直接写可执行脚本。

## 当下痛点

### 1. 进入应用繁琐

公司通常提供统一门户，进入邮件、禅道、OA 等应用往往都要从主入口走一遍。Session 超时后还要重复登录。对每天在多应用间来回切换的用户，这是大量低价值劳动。

### 2. 周报 / 总结难写

每天若不主动记事，周报时想不起做过什么；到年度总结更无法量化、无法汇报。工作过程没有沉淀，汇报只能靠回忆。

### 3. 消息与待办缺少主动提醒

邮件、禅道 Bug 等需要**主动登录应用内查询**，忘记就会拖进度。口头答应的待办也缺少可靠的反馈与提醒机制。

## 产品切入点

浏览器仍是多数办公系统的主入口，因此：

- **Chrome 扩展（Browser Agent）** 作为用户侧切入点：录制、触发、轻量交互；
- **Tauri 桌面应用（Desktop Agent）** 承接扩展权限做不到的事：程序执行、本地存储、CLI、系统通知、后台定时；
- **AI Runtime（agent-core）** 作为本地运行时：Workflow DSL、Tool Registry、凭证与记忆、模型调用。

扩展与桌面应用通信，完成用户交办事项；桌面端挂在后台时，也可定时执行扫描、提醒等事务。

## 设计原则（摘要）

1. **本地优先**：数据与凭证默认落在本机（如 `~/.workcopilot`），Runtime 只监听 `127.0.0.1`。
2. **DSL 中间层**：录制结果与 AI 建议都落到可校验的 Workflow DSL，经 Tool Registry 执行；禁止模型直接生成业务 JS 并执行。
3. **分工清晰**：浏览器侧采集与交互；桌面侧执行与调度；Runtime 统一协议与状态。
4. **先小后组**：不鼓励一次录制超长复杂流；优先短流程，再通过工作流组合拼出完整链路。
